Priority Model

PriorityMeaningEvaluated
Group priority 5Highest priority group1st
Group priority 3Mid priority group2nd
Group priority 1Low priority group3rd
Ungrouped (NULL)COALESCE(priority, 0) = 0Last

Within a Group

Rules within the same group are ordered by created_at DESC (newest first). First-match-wins: once a transaction matches any rule, no later rule can overwrite that match.

SELECT r.*, rg.priority AS group_priority
FROM override_rules r
LEFT JOIN rule_groups rg ON r.group_id = rg.id
ORDER BY COALESCE(rg.priority, 0) DESC, r.created_at DESC

Priority Cascade Logic

src/main/services/rules.ts:557-583

When creating/updating a group at priority N and that slot is already taken:

  1. Find all groups with priority ≥ N, ordered ASC
  2. Walk forward: each consecutive match gets bumped +1
  3. Stop at the first gap
  4. Apply bumps in reverse order (highest first) to avoid unique constraint violations
// Example: Insert at priority 3 into existing [1, 2, 3, 4, 7]
// Cascade: 3→4, 4→5 (stop — gap before 7)
// Result: [1, 2, 3, 4, 5, 7]  ← new group takes slot 3
NOT AN ISSUE: Sequential Priority Updates

Cascade is Fine at ≤100 Groups

RealityMax ~100 rule groups. Worst case: 100 consecutive groups cascade = 100 sequential UPDATE queries. At <1ms each that's <100ms total — well within acceptable range for an infrequent admin operation.
No action neededThis would only be a concern with thousands of groups. The existing sequential approach is fine here.
No fix needed

Documented here for completeness only. The cascade approach is correct and performant at ≤100 groups.

BREAKS: N+1 Query Problem — One SQL Query Per Rule

500K Rules = 500K Sequential SQL Queries

Query count500,000 sequential queries, each scanning up to 5M transactions. At 2ms each = 16+ minutes per evaluation.
MemorylistAllRules() loads all 500K rules into a JS array with parsed JSON. ~500 bytes/rule × 500K = ~250MB just for rule objects.
Map growthThe matched Map can hold up to 5M entries (~500MB at ~100 bytes/entry).
Fix — Single-Pass SQL Evaluation via Temp Table

Instead of querying once per rule, materialize all rules into a temp table and use DuckDB's JOIN engine to match everything in one pass:

-- 1. Create temp table with one row per rule-condition
CREATE TEMP TABLE _rule_conditions AS
SELECT
  r.id          AS rule_id,
  r.target_taxonomy_node_id,
  rg.priority   AS group_priority,
  r.created_at,
  -- Denormalize the single most common condition type for fast SQL matching:
  json_extract_string(r.grouped_conditions, '$.groups[0].conditions[0].field')  AS field0,
  json_extract_string(r.grouped_conditions, '$.groups[0].conditions[0].value')  AS value0
FROM override_rules r
LEFT JOIN rule_groups rg ON r.group_id = rg.id
WHERE r.is_active = TRUE
ORDER BY COALESCE(rg.priority, 0) DESC, r.created_at DESC;

-- 2. For simple supplier-name rules (the majority), one JOIN matches everything:
SELECT DISTINCT ON (t.id)
  t.id            AS txn_id,
  rc.rule_id,
  rc.target_taxonomy_node_id
FROM transactions t
JOIN _rule_conditions rc
  ON rc.field0 = 'supplier_name'
  AND ps.supplier_name = rc.value0
JOIN project_suppliers ps ON t.project_supplier_id = ps.id
ORDER BY t.id, rc.group_priority DESC, rc.created_at DESC;

Rules with complex multi-condition logic still need per-rule evaluation, but simple supplier-name rules (likely 80%+ of all rules) collapse to a single JOIN.

BREAKS: Preview + Apply Runs Full Evaluation Twice

No Caching Between Preview and Apply

Double costThe preview result (which transactions match which rules) is discarded. Apply runs the identical evaluateRules from scratch. At 500K rules, this runs the N+1 problem twice.
Batch updatesapplyRules calls updateTransactions once per (ruleId, targetNodeId) batch. If 500K rules each match distinct transactions = 500K sequential UPDATEs.
Fix — Return a Batch Token from Preview

Store the evaluation result server-side keyed by a short-lived token. Apply references the token instead of re-evaluating:

// previewRules returns a token:
async previewRules(ruleIds: string[]): Promise<{
  token: string;
  affectedRowCount: number;
  matchingRuleCount: number;
}> {
  const matched = await this.evaluateRules(undefined, ruleIds);
  const token = uuidv4();
  this.previewCache.set(token, { matched, expiresAt: Date.now() + 5 * 60_000 });
  return { token, affectedRowCount: matched.size, ... };
}

// applyRules accepts optional token:
async applyRules(ruleIds: string[], token?: string): Promise<...> {
  const matched = token && this.previewCache.get(token)?.matched
    ?? await this.evaluateRules(undefined, ruleIds);
  this.previewCache.delete(token!);
  // ... batch updates
}

For batch UPDATEs: collect all (txnId → targetNodeId) pairs and run a single UPDATE transactions SET ... WHERE id IN (...) per target node, rather than one per rule.

8. Conflict Detection

src/main/services/rules.ts:256-297

How Conflicts Work

  1. Run evaluateRules(candidateIds) — which existing rule wins each candidate?
  2. Look up that existing rule's group priority
  3. Compare against new rule's group priority:
    • Existing priority > new priority → BLOCKED (conflict)
    • Existing priority ≤ new priority → eligible (new rule supersedes)

Key Point

Equal priority = no conflict. A new rule at the same priority level can take over. Only strictly-higher-priority existing rules block. However, the conflict preview doesn't show which rule within the same group would win (determined by created_at DESC ordering) — it just marks all same-priority transactions as eligible.

MultiplierevaluateRules is called once per supplier. Each call runs all 500K active rules. 10K suppliers × 500K rules = 5B queries. At 0.5ms each = 29 days.

Fix — Pre-index Rules by Supplier, Evaluate Once

Most rules have a supplier_name equals X condition. Build an in-memory index before the supplier loop, then only evaluate rules relevant to each supplier:

// Before the supplier loop — build supplier → ruleIds index:
const allRules = await this.rules.listAllRules();
const rulesBySupplier = new Map<string, OverrideRule[]>();
const rulesWithoutSupplier: OverrideRule[] = [];

for (const rule of allRules.filter(r => r.isActive)) {
  const supplierCond = rule.groupedConditions.groups
    .flatMap(g => g.conditions)
    .find(c => c.field === 'supplier_name' && c.operator === 'equals');

  if (supplierCond) {
    const name = String(supplierCond.value).toLowerCase();
    if (!rulesBySupplier.has(name)) rulesBySupplier.set(name, []);
    rulesBySupplier.get(name)!.push(rule);
  } else {
    rulesWithoutSupplier.push(rule); // multi-condition rules — must run for all
  }
}

// Inside the supplier loop — evaluate only relevant rules:
const relevantRules = [
  ...(rulesBySupplier.get(supplier.supplier_name.toLowerCase()) ?? []),
  ...rulesWithoutSupplier,
];
const ruleMatches = await this.rules.evaluateRulesFromList(relevantRules, txnIds);

For a typical dataset where 95%+ of rules are supplier-name rules, this reduces 500K evaluations per supplier down to ~2-5. The 5B queries becomes ~50K-100K.

Fix — Push Filterable Conditions to SQL

Rule property fields (rule_name, rule_source, rule_is_active, rule_category_a) can be translated directly to SQL WHERE clauses, avoiding the JS load entirely for most use cases:

// Translate property-based filter conditions to SQL before loading:
function buildRulePropertySQL(filter: GroupedFilter): string | null {
  const clauses: string[] = [];
  for (const group of filter.groups) {
    for (const cond of group.conditions) {
      switch (cond.field) {
        case 'rule_name':
          clauses.push(`LOWER(r.name) LIKE LOWER('%${cond.value}%')`); break;
        case 'rule_source':
          clauses.push(`r.source = '${cond.value}'`); break;
        case 'rule_is_active':
          clauses.push(`r.is_active = ${cond.operator === 'is_true'}`); break;
        case 'rule_category_a':
          clauses.push(`r.category_a_supplier = ${cond.operator === 'is_true'}`); break;
        case 'rule_group':
          // handled via JOIN
          break;
      }
    }
  }
  return clauses.length ? clauses.join(' AND ') : null;
}

// Apply SQL filter first, then do in-memory match only for complex conditions:
const sqlWhere = buildRulePropertySQL(filter);
const rows = sqlWhere
  ? await this.db.all(`SELECT ... FROM override_rules r WHERE ${sqlWhere}`)
  : await this.listAllRules();

For filters that only use property fields (the common case), this avoids loading the JS rule objects entirely.

 * Pure function: decompose GroupedFilter into relational rows.
 * Called at write time + once for backfill migration.
 */
function decomposeConditions(
  ruleId: string,
  grouped: GroupedFilter
): ConditionRow[] {
  const rows: ConditionRow[] = [];
  for (let gi = 0; gi < grouped.groups.length; gi++) {
    const group = grouped.groups[gi];
    for (let ci = 0; ci < group.conditions.length; ci++) {
      const c = group.conditions[ci];
      rows.push({
        rule_id: ruleId,
        group_idx: gi,
        condition_idx: ci,
        field: c.field,
        operator: c.operator,
        value: c.value ?? null,
        group_connector: grouped.groupConnector ?? 'AND',
        condition_connector: 'AND',
      });
    }
  }
  return rows;
}

async createRule(input: OverrideRuleCreate): Promise<{ id: string }> {
  // Validate FK targets
  if (input.targetTaxonomyNodeId) {
    const node = await this.db.get('SELECT id FROM taxonomy WHERE id = ?', input.targetTaxonomyNodeId);
    if (!node) throw new Error(`Taxonomy node not found: ${input.targetTaxonomyNodeId}`);
  }

    if (!grp) throw new Error(`Rule group not found: ${input.groupId}`);

  const supplierId = supplierName
    ? (await this.suppliers.getProjectSupplierByName(supplierName))?.id ?? null
    : null;

  try {
    await this.db.run(

         (id, name, grouped_conditions, target_taxonomy_node_id,
          group_id, is_active, source, category_a_supplier, project_supplier_id)
       VALUES (?, ?, ?, ?, CAST(? AS VARCHAR), TRUE, ?, ?, ?)`,

      input.targetTaxonomyNodeId, input.groupId ?? null,
      input.source ?? 'manual', input.categoryASupplier ?? false,
      supplierId
    );

    // Decompose and insert conditions
    const condRows = decomposeConditions(id, input.groupedConditions);
    for (const chunk of chunks(condRows, 500)) {
      const placeholders = chunk.map(() => '(?, ?, ?, ?, ?, ?, ?, ?)').join(',');

        r.rule_id, r.group_idx, r.condition_idx,
        r.field, r.operator, r.value,
        r.group_connector, r.condition_connector
      ]);
      await this.db.run(

      );
    }

    await this.db.run('COMMIT');
  } catch (e) {
    await this.db.run('ROLLBACK');
    throw e;
  }

}

  const ctes: string[] = [];
  const requiredJoins = new Set<string>();

  for (let i = 0; i < pairs.length; i++) {
    const { field, operator } = pairs[i];
    const colExpr = FILTER_VIRTUAL_EXPRS[field] ?? `t."${field}"`;
    const predicate = OPERATOR_JOIN_TEMPLATES[operator]?.(colExpr);
    if (!predicate) continue;

    const joinKey = VIRTUAL_COLUMN_REGISTRY[field]?.requiredJoin;
    if (joinKey) requiredJoins.add(joinKey);

    const isNullaryOp = ['is_null', 'is_true', 'is_false'].includes(operator);

    ctes.push(`fo_${i} AS (
    SELECT rc.rule_id, rc.group_idx, rc.condition_idx, t.id AS txn_id
    FROM rule_conditions rc
    JOIN transactions t ON ${isNullaryOp ? 'TRUE' : predicate}
    ${buildJoinsForField(field)}
    JOIN override_rules r ON rc.rule_id = r.id AND r.is_active = TRUE
    WHERE rc.field = '${field}' AND rc.operator = '${operator}'
    ${isNullaryOp ? `AND ${predicate}` : ''}
  )`);
  }

  return { ctes, requiredJoins };
}

Step 2: Full Evaluation Query

WITH
  ${fieldOperatorCTEs},  -- fo_0, fo_1, ... (one per field×operator pair)

  -- Union all matched conditions into a single stream
  condition_evals AS (
    SELECT rule_id, group_idx, condition_idx, txn_id FROM fo_0
    UNION ALL
    SELECT rule_id, group_idx, condition_idx, txn_id FROM fo_1
    -- ... (one SELECT per CTE)
  ),

  -- AND-within-group: all conditions in the group must match
  group_evals AS (
    SELECT
      ce.rule_id, ce.txn_id, ce.group_idx,
      rc_meta.group_connector,
      COUNT(*) = MAX(rc_meta.total_conditions) AS group_matched
    FROM condition_evals ce
    JOIN (
      SELECT rule_id, group_idx, group_connector,
             COUNT(*) AS total_conditions
      FROM rule_conditions
      GROUP BY rule_id, group_idx, group_connector
    ) rc_meta ON ce.rule_id = rc_meta.rule_id
            AND ce.group_idx = rc_meta.group_idx
    GROUP BY ce.rule_id, ce.txn_id, ce.group_idx, rc_meta.group_connector,
             rc_meta.total_conditions
  ),

  -- Aggregate across groups (AND/OR connectors)
  rule_evals AS (
    SELECT rule_id, txn_id,
      BOOL_OR(group_matched) AS any_group_matched,
      BOOL_AND(group_matched) AS all_groups_matched,
      BOOL_OR(group_connector = 'OR') AS has_or_connector
    FROM group_evals
    GROUP BY rule_id, txn_id
  ),

  rule_matches AS (
    SELECT rule_id, txn_id FROM rule_evals
    WHERE CASE WHEN has_or_connector THEN any_group_matched
               ELSE all_groups_matched END
  )

async evaluateRulesBulk(

): Promise<Map<string, { ruleId: string; targetTaxonomyNodeId: string }>> {

  // 1. Get distinct (field, operator) pairs from active rules
  const pairs = await this.db.all<{ field: string; operator: string }>(`
    SELECT DISTINCT rc.field, rc.operator
    FROM rule_conditions rc
    JOIN override_rules r ON rc.rule_id = r.id
    WHERE r.is_active = TRUE
  `);
  if (pairs.length === 0) return new Map();

  // 2. Generate equi-JOIN CTEs

    : '';
  const scopeWhere = !opts.scopeTable && opts.scopeIds
    ? `AND t.id IN (${opts.scopeIds.map(() => '?').join(',')})`
    : '';

  // 4. Assemble + execute
  const sql = buildEvaluationQuery(ctes, scopeJoin, scopeWhere);

About This Tab

This tab documents the reasoning behind the key decisions in the Proposed System. The proposed tab contains the what; this tab contains the why.

1. Why rule_conditions (Persistent Relational Table)

Problem

The current system stores conditions as a JSON blob (grouped_conditions) on each rule. Every evaluation requires JS to parse the JSON, generate SQL per rule, and execute it — creating an N+1 loop (one query per rule).

Decision

Add a rule_conditions table as a materialized projection of the JSON. The JSON column is kept as source of truth for UI/editing; the relational table enables SQL-native bulk evaluation.

Alternatives Considered

  • Replace JSON entirely: Would require migrating all UI code that reads/writes grouped_conditions. Too much churn for the same result.
  • DuckDB JSON functions: DuckDB can query JSON directly, but can't optimize JOIN predicates through JSON extraction. Still requires full table scans.

Risk: Sync Drift

If grouped_conditions JSON and rule_conditions rows diverge, evaluation produces wrong results silently. Mitigated by wrapping both writes in a single DuckDB transaction and adding a startup validation check that compares row counts.

2. Why Equi-JOIN Per (Field, Operator) — Not CROSS JOIN

The CROSS JOIN Failure

The initial V2 design used a single CROSS JOIN with a CASE WHEN dispatch to evaluate all conditions against all transactions in one query. Benchmarked on lifepoint-100k-03-24.c91 (100K transactions, 1000 rules, 1001 conditions):

ApproachTimeIntermediate Rows
Current N+1 loop (1000 sequential queries)552msN/A
V2 CROSS JOIN + CASE WHEN157,005ms (2.6 min)100.1M
Equi-JOIN CTEs220ms~100K (matches only)

Root Cause

The CASE WHEN dispatch is a row-level scalar expression, not a join predicate. DuckDB cannot look inside CASE rc.operator WHEN 'equals' THEN CASE rc.field WHEN 'supplier_name' THEN ps.supplier_name = rc.value END END and recognize it as an equi-join. It must materialize every (condition × transaction) pair and evaluate the expression on each.

The Fix

Instead of one CROSS JOIN with opaque CASE WHEN, generate a separate CTE for each (field, operator) pair with a proper join predicate:

  • Hash-join complexity: O(conditions + transactions) per CTE, not O(conditions × transactions)
  • Only matching rows flow through
  • Predicate pushdown: DuckDB pushes rc.field = 'supplier_name' into the scan
  • Constant CTE count: Even 500K rules using supplier_name = X produce 1 CTE

Scaling Projections

ScenarioCurrent (N+1)CROSS JOINEqui-JOIN
100K txns × 1K rules 547ms 157,005ms 220ms
5M txns × 500K rules ~16 min OOM / hours seconds to low minutes

Why the 100K benchmark gain is modest (2.5x): With only 2 distinct field×operator pairs and 1000 rules, the N+1 loop is already fast (~0.5ms/query). The advantage grows with rule count — at 500K rules, N+1 takes 16 min while equi-JOIN remains a single query.

3. Why Single evaluateRulesBulk() — Not Split Evaluation

The Split Evaluation Problem

An earlier design split evaluation into two passes: a fast equi-JOIN for simple supplier-name rules, and a per-rule loop for complex multi-condition rules. This breaks when a complex rule in a higher-priority group should win over a simple rule in a lower-priority group.

Example

RuleGroup PriorityTypeConditionsTarget
rule-A10 (high)Complexsupplier = 'Acme' AND amount > 50Ktax-Strategic-IT
rule-B1 (low)Simplesupplier = 'Acme'tax-IT-General

Transaction tx-1: supplier = Acme, amount = $100K.

  • Correct: rule-A wins (priority 10 > 1) → tax-Strategic-IT
  • Split-eval: If simple JOIN runs first and claims tx-1 for rule-B, the complex pass never gets a chance.

First-match-wins semantics require a single ordered evaluation across all rule types. The equi-JOIN CTE approach achieves this — all rule types contribute CTEs to the same query, and DISTINCT ON ... ORDER BY priority picks the winner in one pass.

4. COUNT vs BOOL_AND in group_evals

Problem

The CROSS JOIN approach (V2) produced a matched boolean for every (condition × transaction) pair — including non-matches. BOOL_AND(matched) naturally checked "did all conditions pass?"

With equi-JOINs, non-matching pairs don't appear in the result at all (filtered out by the JOIN predicate). There's nothing to BOOL_AND over — only matches exist.

Solution

Count how many conditions in each group matched and compare against the total:

COUNT(*) = MAX(rc_meta.total_conditions) AS group_matched

If 3 out of 3 conditions matched → the group passes. If only 2 out of 3 appeared in condition_evals → one condition didn't match → group fails. Semantically equivalent to BOOL_AND but works with inner-join results.

5. NOT Operator Strategy

Negation operators (not_equals, not_contains) present a subtlety: supplier_name != 'Acme' as a JOIN predicate matches every other supplier, producing a massive result set.

Decision: Anti-JOIN Pattern

For negation, find rows that DO match the positive version, then exclude them. Alternatively, use a small CROSS JOIN scoped to just the negation conditions.

Practical observation: Negation operators are <1% of real rules. A CROSS JOIN for just these few conditions is cheap — the expense of the V2 CROSS JOIN was applying it to all conditions.

Virtual columns (e.g., supplier_name lives on project_suppliers, not transactions) require subqueries to materialize the resolved column:

-- For supplier_name (virtual column via JOIN):
SELECT rc.rule_id, rc.group_idx, rc.condition_idx, txn.id AS txn_id
FROM rule_conditions rc
JOIN (
  SELECT t.id, ps.supplier_name
  FROM transactions t
  LEFT JOIN project_suppliers ps ON t.project_supplier_id = ps.id
) txn ON txn.supplier_name = rc.value
JOIN override_rules r ON rc.rule_id = r.id AND r.is_active = TRUE
WHERE rc.field = 'supplier_name' AND rc.operator = 'equals'

-- For physical columns (direct join):
SELECT rc.rule_id, rc.group_idx, rc.condition_idx, t.id AS txn_id
FROM rule_conditions rc
JOIN transactions t ON t."account_description" = rc.value
JOIN override_rules r ON rc.rule_id = r.id AND r.is_active = TRUE
WHERE rc.field = 'account_description' AND rc.operator = 'equals'

7. OR-Within-Group

Current data uses AND-within-group universally. The COUNT = total_conditions check in group_evals implements AND semantics. If OR-within-group is ever needed, the check switches to COUNT > 0 for OR groups. This should be validated against actual data before implementing.

8. Supplier FK vs String Denormalization

An earlier design used supplier_name_denorm (a string copy of the supplier name). This creates staleness: renaming a supplier breaks all rules referencing the old name.

Decision: project_supplier_id FK

  • Renames are free: FK points to the same row regardless of name changes
  • Merges require one UPDATE: reassignSupplierRules(losingIds, survivorId)
  • No JSON sync needed: The groupedConditions JSON still has the old name for display, but the FK drives the JOIN
