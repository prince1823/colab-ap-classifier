Classification Pipeline

What changed: The original single-call approach (full taxonomy per supplier) was split into two sequential LLM calls per supplier — a Call 1 supplier-level category selection (batched at 10) and a Call 2 transaction-level L3 classification. This reduces taxonomy tokens per supplier and focuses each LLM call on one concern.

Why Call 2 can't be batched

Call 2 dedup groups are numbered sequentially starting at 1 per supplier. Batching multiple suppliers would create group numbering collisions, and cross-supplier transaction context would confuse the LLM about which transactions belong to which supplier. Per-supplier is the only viable approach.

Orchestration order

classifyAll():
  1. Chunk suppliers into batches of 10
  2. Run all Call 1 batches concurrently (pool of 5)
     → collect Map<supplierId, categoryPath>
  3. Run all Call 2s concurrently (pool of 5)
     each reads its supplierId's categoryPath from the map

  Stop check: isStopped flag checked before each phase.
  In-flight calls complete; results discarded if stopped.
Call 1 batches are fully resolved before any Call 2 starts. This prevents Call 2 slots from blocking on category selection and keeps the two phases cleanly separated for logging and retry logic.

QC Agent — Full Specification

Role distinction: Classification produces a deterministic baseline — same logic every run, no user input. QC is where the user takes control — they choose what to review, what rules to apply, and can run QC multiple times with different configurations. Any QC change gets flagged for human review.

QC Pipeline Flow

1
Resolve scoped suppliers
Apply scope: FilterCondition[] to all suppliers with classified transactions. Compute per-supplier fields: total_spend, transaction_count, num_categories, is_tail_spend, is_researched.
SELECT ps.id, ps.supplier_name, ps.is_tail_spend, ps.is_researched,
       COUNT(t.id) as transaction_count,
       COALESCE(SUM(TRY_CAST(t.spend_amount AS DOUBLE)), 0) as total_spend,
       COUNT(DISTINCT t.taxonomy_node_id) as num_categories
FROM project_suppliers ps
JOIN transactions t ON t.project_supplier_id = ps.id
WHERE t.classification_status IN (classified statuses)
GROUP BY ps.id, ps.supplier_name, ps.is_tail_spend, ps.is_researched
2
Algorithmic pass (if enabled)
Spend-weighted consolidation for suppliers with >1 L3 category. Runs on all scoped suppliers.
Algorithmic Consolidation logic
▼

L3 pass

If ≥ l3_threshold (default 0.95) of spend is in one L3 category → consolidate outlier transactions into that dominant L3.

L2 pass

If ≥ l2_threshold (default 0.90) of spend is in one L2, AND ≥ l3_threshold of that L2's spend is in one L3 → consolidate outliers across L3s within that L2 into the dominant.

Result

Each supplier tagged with algorithmic_resolved = true/false. Consolidated transactions: classification_status = 'classified_by_qc_agent', flagged_for_review = true.

3
LLM pass (if enabled)
Filter scoped suppliers by gate_conditions. Per matching supplier: build full supplier summary → single LLM call with user rules → apply group-level recommendations.
LLM Full detail
▼

Gate conditions determine which scoped suppliers get LLM review. Default: algorithmic_resolved = false (only review what algorithmic didn't resolve).

Per matching supplier:

  • Build full supplier summary via buildSupplierSummary()
  • Single LLM call: system prompt (hardcoded) + user prompt (summary + user rules)
  • Parse response: validate group numbers, fuzzy-match taxonomy paths
  • Apply valid recommendations, skip invalid ones with warning
4
Flag all changes
Every transaction modified by QC: classification_status = 'classified_by_qc_agent' + flagged_for_review = true. No exceptions.

QC Configuration

Stored in project_settings.qc_config. Fully user-configurable.

interface QCConfig {
  scope: FilterCondition[];              // which suppliers to process
  algorithmic: {
    enabled: boolean;                    // default true
    l3Threshold: number;                 // default 0.95
    l2Threshold: number;                 // default 0.90
  };
  llm: {
    enabled: boolean;                    // default true
    gateConditions: FilterCondition[];   // which scoped suppliers get LLM review
    rules: string;                       // user prompt injected into LLM call
  };
}

Default config (out of the box)

{
  scope: [],  // all suppliers
  algorithmic: { enabled: true, l3Threshold: 0.95, l2Threshold: 0.90 },
  llm: {
    enabled: true,
    gateConditions: [
      { field: 'algorithmic_resolved', operator: 'is_false' }
    ],
    rules: DEFAULT_QC_RULES
  }
}

Default behavior: algorithmic consolidation runs on everything; LLM reviews only what algorithmic didn't resolve.

Gate condition fields

Available for both scope and gate_conditions. Computed per-supplier at QC runtime.

FieldTypeDescription
is_tail_spendbooleanFrom project_suppliers.is_tail_spend
is_researchedbooleanFrom project_suppliers.is_researched
total_spendnumberSum of spend_amount for supplier's transactions
transaction_countnumberCount of transactions
num_categoriesnumberDistinct L3 classifications after classification

FilterConditionQC vs FilterCondition: These fields don't exist in the transactions table — they're computed at QC runtime and evaluated in-memory against SupplierQCData objects. This is why FilterConditionQC is a separate type with QC-specific operators (is_true, is_false).

Application steps

  • 1. Map groupNumbers → transaction IDs (via dedup group mapping, same as classification)

Design principles

Classification is deterministic

One supplier → one L1|L2 → L3 assignments. No multi-L2 per supplier. No user configuration — same logic every run. Produces a consistent baseline.

QC is user-controlled

User decides: which suppliers to review (scope), when to use LLM (gate conditions), what the LLM checks (rules prompt). Any QC change gets flagged.

Tail spend is not special
