Frontend Architecture (Target State)

Colab91 AP Classifier — Page Map, Functionalities, Component Ownership, and Type Contracts

Overview

The frontend is a React app running inside Electron's renderer process. It communicates with the main process exclusively via typed IPC. The UI is organized as a linear 5-step workflow (Upload → Data Review → Classification → Review → Output) with a project setup sidebar (Company Context, Taxonomy, Suppliers, Override Rules, Version History).

Guiding Principles

  • Pages call ipc directly — pages compose components and call the typed IPC facade. No intermediate "feature service" layer. Simple page logic (call IPC, update state, refetch) stays in the page.
  • Complex logic lives in hooks, not services — when a page has genuinely complex orchestration (Review page: undo/redo, reclassification, filter state), extract it into custom hooks. Hooks are the React way; service classes are the Angular way.
  • Shared DTOs are the view models (usually) — for most pages, the shared type IS what the UI displays. Only the Review page needs a real transform (Transaction → DashboardTransactionRow). Don't create view model wrappers for types that map 1:1.
  • No implicit any — every filter, drag item, undo entry, pivot row, and callback payload is typed.
  • IPC is compile-checked — a single IPCInvokeMap in shared types ensures channel names, argument shapes, and return types are validated end-to-end.

What We Explicitly Don't Do

  • No feature services layer — renderer/services/ modules would be thin wrappers around ipc.xxx() calls. The IPC facade already IS the abstraction over the main process. Adding another layer just moves 3-5 lines of code to a different file.
  • No DI via React Context for services — in Electron, the IPC boundary is the DI boundary. You don't need to inject a supplierService when ipc.suppliers.list() already abstracts the implementation.
  • No separate view-models.ts for every page — CompanyContext, TaxonomyNode, OverrideRule, ChangeLog etc. map 1:1 to what the UI shows. Only DashboardTransactionRow justifies a dedicated transform.

┌──────────────────────────────────────────────────────────────────────────┐ │ Upload Transactions │ │ │ │ ┌────────────────────────────────────────────────────────────────────┐ │ │ │ │ │ │ │ Drag & drop a CSV file here, or click to browse │ │ │ │ │ │ │ │ [ Select File ] │ │ │ │ │ │ │ └────────────────────────────────────────────────────────────────────┘ │ │ │ │ ── After file selected ──────────────────────────────────────────────── │ │ │ │ CSV Preview (first 5 rows) │ │ ┌──────────┬──────────────┬──────────┬──────────┬────────────────────┐ │ │ │ Vendor │ Amount │ GL Code │ Desc │ Date │ │ │ ├──────────┼──────────────┼──────────┼──────────┼────────────────────┤ │ │ │ Acme Co │ 1,234.56 │ 6100 │ Software │ 2024-01-15 │ │ │ │ ... │ ... │ ... │ ... │ ... │ │ │ └──────────┴──────────────┴──────────┴──────────┴────────────────────┘ │ │ │ │ Column Mapping │ │ ┌─────────────────────┬────────────────────┐ │ │ │ CSV Column │ Maps To │ │ │ ├─────────────────────┼────────────────────┤ │ │ │ Vendor │ supplier_name [v] │ │ │ │ Amount │ spend_amount [v] │ │ │ │ GL Code │ gl_code [v] │ │ │ │ Desc │ gl_description [v] │ │ │ │ Date │ invoice_date [v] │ │ │ └─────────────────────┴────────────────────┘ │ │ │ │ [Import X,XXX Rows] │ └──────────────────────────────────────────────────────────────────────────┘

Functionality

  1. File Selection — Drag-drop zone or native file dialog via ingest:selectFile
  2. CSV Preview — ingest:parseCSV returns columns, sample rows (5), total count
  3. Column Mapping — System checks for stored mappings from previous uploads. If none match, ingest:suggestMappings uses LLM to suggest. User reviews/adjusts via dropdown selectors.
  4. Import — ingest:importCSV creates transactions with mapped columns. Mappings stored in uploads table for reuse.
  5. Draft Persistence — selected file path and mappings saved as upload draft in Zustand store (survives navigation away and back)

┌──────────────────────────────────────────────────────────────────────────┐ │ Review Dashboard │ │ │ │ ┌────────────────────────────────────────────────────────────────────┐ │ │ │ [Tables] [Pivot] [Metrics] Active Filters: L1=IT │ │ │ └────────────────────────────────────────────────────────────────────┘ │ │ │ │ ┌──────────────┬─────────────────────────────────────────────────────┐ │ │ │ Taxonomy │ Transaction Table │ │ │ │ Tree │ ┌────────┬────────────┬──────────┬──────────────┐ │ │ │ │ │ │Supplier│ Amount │ L1 > L2 │ Status │ │ │ │ │ [-] Corp Svc │ ├────────┼────────────┼──────────┼──────────────┤ │ │ │ │ [-] IT │ │ Acme │ $1,234 │ IT > SW │ AI classified│ │ │ │ │ Software │ │ Beta │ $567 │ IT > HW │ Rule match │ │ │ │ │ Hardware │ │ Gamma │ $890 │ IT > SW │ Unclassified │ │ │ │ │ Licenses │ │ ... │ ... │ ... │ ... │ │ │ │ │ [-] HR │ └────────┴────────────┴──────────┴──────────────┘ │ │ │ │ Payroll │ │ │ │ │ Benefits │ Selected: 3 rows [Reclassify] [Accept] │ │ │ │ [-] Ops │ │ │ │ │ ... │ ┌─ Reclassify Modal ─────────────────────────────┐ │ │ │ │ │ │ Move 3 rows to: [Taxonomy Tree Selector] │ │ │ │ │ │ │ [Confirm] [Cancel] │ │ │ │ │ │ └────────────────────────────────────────────────┘ │ │ │ └──────────────┴─────────────────────────────────────────────────────┘ │ └──────────────────────────────────────────────────────────────────────────┘

Sub-Views

Tables View (default)

  • Left panel: taxonomy tree for filtering (click node to filter transactions)
  • Main area: transaction table with sortable columns, row selection, inline status
  • Multi-select + bulk reclassify: select rows, choose new taxonomy node, confirm
  • Drag-and-drop: drag selected rows onto taxonomy tree node to reclassify
  • Accept: mark selected rows as human_reviewed = true
  • Undo/redo stack (20 entries) for reclassification actions

Pivot View

  • Hierarchical pivot table: rows are taxonomy levels (L1 → L2 → L3), values are spend amounts
  • Expand/collapse nodes, search filter, export to Excel
  • Click a pivot cell to drill down into filtered transaction view
  • Configurable aggregation: sum, count, average

Metrics View

  • Summary cards: classification rate, review rate, top categories, top suppliers
  • Spend visualizations: category breakdown, supplier concentration
  • Expandable metric sections for detailed drill-down

Functionality

  1. Data Loading — Progressive chunk loading (5000 rows/chunk) via useTransactions hook
  2. Filtering — By taxonomy node, classification status, supplier, text search. Filters stored in Zustand.
  3. Reclassification — Select rows + new taxonomy node → transactions:update with new taxonomy_node_id + human_reviewed = true
  4. Undo/Redo — Stack of reclassification actions. Undo via changelog:revert.
  5. Pivot — Client-side aggregation via useHierarchicalPivotData hook
  6. Feedback Suggestions — System-generated reclassification suggestions (planned feature)

Functionality

  1. Changelog List — All changes from changelog:list, newest first
  2. Expandable Detail — Click to see before/after values, affected row IDs
  3. Taxonomy Resolution — Loads taxonomy nodes to display human-readable paths instead of IDs
  4. Revert — Undo a change via changelog:revert (restores old values)

Refactor Plan (3 Tiers)

Practical, prioritized cleanup. No new abstraction layers. Fix what's broken, type what's loose, extract what's tangled.

Architecture: Keep It Simple

DATA FLOW (this is all we need): Page/Component ──▶ Typed IPC Facade (ipc.ts) ──▶ preload ──▶ main IPC handler ──▶ DI service │ └─ IPCInvokeMap ensures compile-time safety on channel, args, and result COMPLEX PAGES (Review only): ReviewPage ──▶ useReclassification() hook ──▶ ipc.transactions.update / ipc.changelog.revert ──▶ useReviewFilters() hook ──▶ local filter state (Zustand) ──▶ useUndoRedo() hook ──▶ changelog IPC + local stack

Why no services layer? In Electron, the IPC facade already IS the abstraction. A "supplierService" calling ipc.suppliers.list() adds a file without adding value. Pages call ipc directly. When page logic gets complex (only the Review page), extract into hooks.

Type Contracts

Tier 2: IPCInvokeMap (Compile-Time IPC Safety)

A single type map in shared/types/ipc-contract.ts defines every channel's argument and return types. Both renderer and main process import from it. ~50 lines, prevents the entire class of "wrong channel / wrong args / wrong return" bugs.

// shared/types/ipc-contract.ts

interface IPCInvokeMap {
  // Project
  'project:new':            { args: [name: string, filePath?: string]; result: { filePath: string; name: string } };
  'project:open':           { args: [filePath?: string]; result: { filePath: string; name: string } };
  'project:close':          { args: []; result: void };
  'project:getSetting':     { args: [key: string]; result: unknown };
  'project:setSetting':     { args: [key: string, value: unknown]; result: void };
  'project:getMetadata':    { args: []; result: ProjectMetadata };
  'project:updateMetadata': { args: [updates: ProjectMetadataUpdate]; result: void };

  // Ingest
  'ingest:selectFile':      { args: []; result: string | null };
  'ingest:parseCSV':        { args: [filePath: string]; result: CSVPreview };
  'ingest:suggestMappings': { args: [columns: string[], sampleRows: Record<string, string>[]]; result: ColumnMappingResult };
  'ingest:importCSV':       { args: [filePath: string, mappings: ColumnMapping]; result: { rowsInserted: number; uploadId: string } };

  // Transactions
  'transactions:query':     { args: [filters?: TransactionFilter]; result: PaginatedTransactions };
  'transactions:stats':     { args: []; result: TransactionStats };
  'transactions:getColumns':{ args: []; result: string[] };
  'transactions:update':    { args: [update: TransactionUpdate]; result: void };

  // Classification
  'classification:start':   { args: []; result: void };
  'classification:cancel':  { args: []; result: void };

  // Taxonomy
  'taxonomy:getNodes':      { args: []; result: TaxonomyNode[] };
  'taxonomy:addNode':       { args: [fullPath: string, description?: string]; result: TaxonomyNode };
  'taxonomy:updateNode':    { args: [nodeId: string, updates: Partial<TaxonomyNode>]; result: void };
  'taxonomy:deleteNode':    { args: [nodeId: string]; result: void };
  'taxonomy:importFromFile':{ args: [filePath: string]; result: void };

  // Suppliers
  'suppliers:list':         { args: []; result: ProjectSupplierView[] };
  'suppliers:update':       { args: [id: string, input: SupplierUpdateInput]; result: void };
  'suppliers:confirm':      { args: [id: string, status: SupplierConfirmationStatus]; result: void };
  'suppliers:researchAll':  { args: []; result: void };
  'suppliers:researchSingle': { args: [supplierName: string]; result: SupplierInfo };

  // Rules
  'rules:list':             { args: []; result: OverrideRule[] };
  'rules:create':           { args: [input: OverrideRuleCreate]; result: { id: string } };
  'rules:update':           { args: [ruleId: string, updates: OverrideRuleUpdate]; result: void };
  'rules:delete':           { args: [ruleId: string]; result: void };

  // Changelog
  'changelog:list':         { args: []; result: ChangeLog[] };
  'changelog:revert':       { args: [changeId: string]; result: void };

  // Export
  'export:csv':             { args: []; result: { rowsExported: number } | null };
}

interface IPCEventMap {
  'classification:progress':        ClassificationProgress;
  'suppliers:research:progress':    ResearchProgress;
}

type Channel = keyof IPCInvokeMap;
type Args<K extends Channel> = IPCInvokeMap[K]['args'];
type Result<K extends Channel> = IPCInvokeMap[K]['result'];

Tier 3: Review Page Types (the one transform that matters)

Most pages use shared DTOs directly — TaxonomyNode, OverrideRule, ChangeLog, CompanyContext etc. map 1:1 to what the UI shows. No view model wrappers needed.

The one exception is the Review page. Its transaction rows need a typed transform because the raw Transaction wire DTO has dynamic canonical fields, and the UI derives l1/l2/l3 from the classification path. This type lives in transactionTransform.ts alongside the transform function — not in a separate view-models file.

// In src/renderer/utils/transactionTransform.ts

/** Row shape used by Review Dashboard, tables, pivot, and metrics.
 *  This is the ONLY view model transform in the app. */
interface DashboardTransactionRow {
  id: string;
  supplierName: string;           // resolved via project_supplier join
  originalSupplierName: string;
  spendAmount: number;
  glDescription: string | null;
  classificationStatus: 'unclassified' | 'classified_by_rule' | 'classified_by_ai';
  humanReviewed: boolean;
  classificationPath: string | null;   // "L1|L2|L3"
  classificationReasoning: string | null;
  l1: string | null;              // derived from classificationPath
  l2: string | null;
  l3: string | null;
  taxonomyNodeId: string | null;
  // Dynamic canonical fields (optional)
  glCode?: string;
  lineDescription?: string;
  costCenter?: string;
  invoiceDate?: string;
  invoiceNumber?: string;
  [key: string]: unknown;         // for truly dynamic fields
}

Data Flow

End-to-End Request Flow

RENDERER Page/Component (or Hook for complex pages) │ calls directly ▼ Typed IPC Facade (src/renderer/lib/ipc.ts) │ invoke<K extends keyof IPCInvokeMap>(channel, ...args) │ unwraps IPCResponse envelope, throws on error ▼ Preload Bridge (contextBridge) │ window.electronAPI.invoke(channel, ...args) ▼ MAIN PROCESS IPC Handler (src/main/ipc/*.ts) │ receives typed args, calls service, wraps in IPCResponse ▼ Service (from DI container) │ business logic, DB queries, LLM calls ▼ Database / External APIs

No intermediate service layer in renderer. The IPC facade IS the abstraction. Pages call ipc.suppliers.list() directly. For the Review page, hooks (useReclassification, useUndoRedo, useReviewFilters) encapsulate multi-step logic.

Event Flow (Progress Streaming)

MAIN PROCESS Service (ClassificationRunner / SupplierResearcher) │ emits to EventBus ▼ EventBus (AppEventBus singleton) │ index.ts subscriber ▼ webContents.send(channel, data) │ ▼ RENDERER Preload Bridge: window.electronAPI.on(channel, callback) │ ▼ Store Adapter (workflowStore subscription in AppShell) │ normalizes event data, updates Zustand ▼ Components (read from store, re-render)
