Guiding Principles (unchanged from v1)

  • Pages call ipc directly — no renderer service layer. The typed IPC facade IS the abstraction.
  • Complex orchestration lives in hooks — when a view has multi-step logic (reclassify, undo/redo, pivot keyboard), extract into custom hooks.
  • No implicit any — every filter condition, drag item, queue entry, and pivot row is typed.
  • IPC is compile-checked — IPCInvokeMap in shared types ensures channel names, args, and return types are validated end-to-end.

Dependency Gate System

Each view declares its own dependencies. DependencyGate reads derived booleans from workflowStore and renders an explanatory message with a link to the blocker instead of the view content.

Dependency Rules

ViewRequired ConditionsGate Message
Project None — always accessible —
Taxonomy None — always accessible —
Data None — always accessible —
Suppliers hasUploadedData (CSV imported + columns mapped) "Upload and map your data first." → Go to Data
Classification hasTaxonomy AND hasConfirmedSuppliers If no taxonomy: "Load a taxonomy before classifying." → Go to Taxonomy
If no confirmed suppliers: "Confirm at least one supplier before classifying." → Go to Suppliers
Review hasClassifiedRows "Run classification first — no classified rows yet." → Go to Classification
Override Rules hasUploadedData (needs columns for condition builder) "Upload data first so columns are available for rule conditions." → Go to Data
Version History None — always accessible —
Design note: Override Rules has no dependency on classified rows (v1 spec was wrong). Rules run before the LLM during classification. They can also be re-applied retroactively after classification via rules:applyAll. Rules can be authored at any time after data is uploaded (so the condition field selector has columns to show).

src/renderer/views/TaxonomyView.tsx
┌──────────────────────────────────────────────────────────────────────────┐ │ Taxonomy [ Import from .txt File ] │ │ │ │ ┌─── Tree ─────────────────────────────────────────────────────────┐ │ │ │ [-] Corporate Services [+ add] │ │ │ │ [-] IT [rename] [+ add] │ │ │ │ Software [rename] [merge] [del] [+ add] │ │ │ │ Hardware [rename] [merge] [del] │ │ │ │ [+] HR │ │ │ │ [-] Operations [+ add] │ │ │ └──────────────────────────────────────────────────────────────────┘ │ │ │ │ ── Add Node ────────────────────────────────────────────────────────── │ │ L1 [ Select or create new ▼ ] │ │ L2 [ Select under L1 or create new ▼ ] │ │ L3 [ Select under L2 or create new ▼ ] (optional — adds at L2 if │ │ left blank) │ │ Description [ ________________________________ ] (L3 only) │ │ [ Add Node ] │ └──────────────────────────────────────────────────────────────────────────┘

Functionality

  1. Import from file: Opens file picker (native Electron dialog via ingest:selectFile filtered to .txt), then calls taxonomy:importFromFile(path). Replaces entire taxonomy if one exists (with confirmation prompt).
  2. Tree view: Expandable L1 → L2 → L3 hierarchy from taxonomy:getNodes. L3 node description shown on hover.
  3. Add node: Inline form below tree. L1 is a combo-select (pick existing or type new). L2 is a combo-select filtered to children of the chosen L1. L3 is optional combo-select filtered to children of chosen L2. If L3 is blank, the node is added at L2 depth. Description is available for L3 nodes only.
  4. Rename: Click rename icon → inline edit → confirm. Calls taxonomy:renameNode.
  5. Merge: Click merge on a node → shows a target picker dialog (select destination node at same depth) → confirm. Calls taxonomy:mergeNodes. All transactions referencing source are moved to target.
  6. Delete: Click delete → backend checks if any transactions reference this node. If yes: block and show message "X rows are classified under this node. Reassign them in Review first." with a link to Review filtered to that node. If no transactions reference it: confirm and call taxonomy:deleteNode.
Delete block flow: taxonomy:deleteNode returns an error if transactions reference the node. Frontend catches this, shows the message with a link to Review filtered to taxonomyNodeId = [nodeId]. The taxonomy service's reassignTo parameter is NOT used from the UI — users must manually reassign in Review, then retry delete.

Data View — 3-Step Stepper (Multi-CSV)

src/renderer/views/DataView.tsx

The Data view is a single sidebar nav item containing a 3-step sequential flow. Steps are not separate routes — step state lives in the DataView component. Users can upload multiple CSVs with different column mappings; each CSV is imported immediately after mapping confirmation. The priority step is visited once after all uploads are complete.

┌──────────────────────────────────────────────────────────────────┐ │ Step 1: Upload CSV ──▶ Step 2: Column Mapping │ │ (file select, (canonical ↔ file col, │ │ upload history, + Add Column, │ │ mapping source choice) Apply & Import) │ │ ▲ │ │ │ └──────────────────────────┘ (loop: add more CSVs) │ └──────────────────────────┬─────────────────────────────────────┘ ▼ Step 3: Column Priority (drag-to-reorder, combined transaction preview, Save Priorities only)

Multi-CSV flow: After each CSV is mapped, ingest:importCSV is called immediately and a default column_priorities is saved (satisfying invariant 5). The user returns to Step 1 where completed uploads are listed. They can add more CSVs or proceed to Step 3 to finalize priority ordering.

  • ingest:parseCSV called on file select → shows file info bar with action buttons inline, CSV preview below.
  • Mapping source choice (after file selected): User explicitly chooses how to derive column mappings:

Functionality

  1. Progress bar (top): Shows progress over classifiable rows only (those with a confirmed supplier). "Z rows blocked — awaiting supplier confirmation" is shown as a link to Suppliers. When all suppliers are confirmed, the blocked count disappears and the bar expands to full row count.
  2. Filter conditions: Uses the universal TransactionFilterCondition / SupplierFilterCondition types. Available fields include:

  7. Live status: While running, shows current supplier name, supplier count progress, and a secondary progress bar. Cancel buttons stop the running operation.

Pivot Table

  • Server-side aggregation via transactions:pivotAggregation (DuckDB GROUP BY). Works on millions of rows — returns only aggregated rows (~hundreds).
  • Default row dimensions: L1 → L2 → L3 (from classification_l1, classification_l2, classification_l3 columns).
  • Expand/collapse nodes to drill into sub-levels.
  • Spend display: Toggle between sum (absolute spend) and percentage (% of filtered total). Both columns shown simultaneously when space permits.
  • [→] drill-down icon on leaf rows: opens a transaction detail panel showing individual rows for that node (paginated table via transactions:query with a filter on that taxonomy node).
  • "Unclassified" row shown at bottom for rows with no taxonomy node.
  • Live updates: If classification is still running (isClassifying), the pivot auto-refreshes every 5 seconds.

Filter Bar

  • Universal FilterConditionBuilder at the top of the view.
  • Filters narrow the pivot aggregation — sent to transactions:pivotAggregation as filters param.
  • System fields available: human_reviewed, classification_status, supplier_name, any canonical column.

Keyboard-Driven Reclassification

Design: The pivot table is keyboard-navigable. Users navigate rows with arrow keys, select a row (or filter state representing a set of transactions), then press a shortcut to open the reclassify modal. This is the primary reclassification flow for power users.

Reclassification flow:

  1. User navigates to a pivot row (e.g. "IT › Software") and presses R
  2. Modal opens. The "scope" is all transactions matching the focused pivot row's implicit filter (e.g. classification_l1 = 'Corporate Services' AND classification_l2 = 'IT' AND classification_l3 = 'Software') PLUS any active top-level filters from the filter bar
  3. Row count is shown ("560 rows currently in: IT › Software")
  4. User types in the search box — "contains" match on full_path of taxonomy nodes. Results filter live.
  5. User selects target node from results list (arrow keys + Enter, or click)
  6. "Confirm" button is shown with the target node and row count. User clicks Confirm (or presses Enter)
  7. Calls transactions:update({ filter: pivotFilter, update: { taxonomyNodeId: targetId, humanReviewed: true } })
  8. Modal closes, pivot refreshes
  9. Undo entry pushed to undo stack (via changelog entry from backend)

refreshGateState()

Called by AppShell on every route change (debounced 50ms). Fetches:

  • transactions:stats → totalRows, classifiedRows
  • taxonomy:getNodeCount → taxonomyNodeCount
  • suppliers:list → count where confirmationStatus === 'confirmed'
  • ingest:getUpload → hasColumnsMapped

Then derives all gate booleans from these counts + projectMetadata fields.

No WorkflowStateContext

Components read Zustand directly via useWorkflowStore(s => s.hasTaxonomy) etc. The DependencyGate component accepts the required booleans as props, so callers pass useWorkflowStore() values explicitly. No React Context layer needed — Zustand is already the single source of truth.

Universal Filter System

A single FilterCondition type is used everywhere — transaction queries, supplier queries, classification queues, and rule conditions. System fields (human_reviewed, classification_status, confirmationStatus) are first-class field names alongside dynamic CSV columns.

FilterCondition (extended)

// shared/types/filters.ts  (replaces FilterCondition in transactions.ts)

type FilterOperator =
  | 'equals' | 'not_equals'
  | 'contains' | 'not_contains'
  | 'starts_with' | 'ends_with'
  | 'regex'
  | 'in_list'                     // value is string[] (comma-sep string in UI)
  | 'greater_than' | 'less_than'
  | 'greater_than_or_equal' | 'less_than_or_equal'
  | 'is_true' | 'is_false';       // NEW: for boolean fields

type FilterConnector = 'AND' | 'OR';

interface FilterCondition {
  field: string;                   // column name or system field
  operator: FilterOperator;
  value: string | number | boolean | string[];
  connector?: FilterConnector;     // default 'AND'
}

// ─── System field names (used across all views) ──────────────────────────

// Transaction system fields
const TRANSACTION_SYSTEM_FIELDS = [
  'human_reviewed',           // boolean — is_true / is_false
  'classification_status',    // 'unclassified' | 'classified_by_rule' | 'classified_by_ai'
  'taxonomy_node_id',         // FK — equals / in_list
  'classification_l1',        // derived — equals / contains
  'classification_l2',        // derived
  'classification_l3',        // derived
] as const;

// Supplier system fields (used in SupplierFilterCondition)
const SUPPLIER_SYSTEM_FIELDS = [
  'confirmationStatus',       // 'pending' | 'confirmed' | 'rejected' | 'merged'
  'dataSource',               // 'universe' | 'web_search' | 'manual'
  'isTailSpend',              // boolean
  'universeMatch',            // boolean
  'totalSpend',               // number
  'transactionCount',         // number
] as const;

// ─── Context-typed filter wrappers ────────────────────────────────────────

interface TransactionFilter {
  conditions: FilterCondition[];
  page?: number;
  pageSize?: number;
  sortBy?: string;
  sortDir?: 'asc' | 'desc';
}

interface SupplierFilter {
  conditions: FilterCondition[];   // fields from SUPPLIER_SYSTEM_FIELDS or supplier name
}

// ─── Classification queue filter ─────────────────────────────────────────
interface ClassificationQueueFilter {
  supplierConditions?: FilterCondition[];    // filter which suppliers to include
  transactionConditions?: FilterCondition[]; // filter which transactions within those suppliers
}
