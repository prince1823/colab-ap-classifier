Undo / Redo Deep Dive

Generated 2026-04-07 — last verified 2026-04-08 — analysis of all state-mutating user actions in the Colab AP Classifier and their undo support.

TL;DR: The codebase has full undo/redo infrastructure (changelog table, revert service, keyboard-shortcut hook), but only 1 of ~42 user actions is actually wired into the undo stack: rules:createAndApply (the reclassification modal). Several other actions write changelog entries but never push to the renderer-side undo stack. Most write paths don't log at all.

1. Existing Infrastructure

1.1 The change_log table

Defined in src/main/services/database.ts:628. Schema:

id, source ('manual'|'pipeline'|'rule'|'feedback'),
affected_table, affected_ids (JSON), affected_count,
old_values (JSON), new_values (JSON),
description, is_reverted, filter_context, rule_id, created_at

1.2 ChangelogStore service

src/main/services/changelog.ts

  • logChange() (line 137) — single insertion entry point; returns the new entry id.
  • revertChange() (line 156) — restores old_values onto the affected rows and flips is_reverted=TRUE. Per commit c7c4123, missing rows no longer throw — they return a warning string so the undo stack stays consistent. Undo works; redo does not — revertChange() throws on an already-reverted entry, so redo always errors out. Fix: make it a toggle (if already reverted, apply new_values and clear the flag).
  • listChanges() / listChangesPaginated() / listByRuleId() — read APIs used by Version History and rule deactivation modal.

1.3 Renderer hook: useUndoRedo

src/renderer/hooks/useUndoRedo.ts

  • In-memory stacks (undoStack, redoStack), MAX_STACK_SIZE = 20.
  • Keyboard shortcuts: Cmd/Ctrl+Z undo, Cmd/Ctrl+Shift+Z redo. Disabled inside INPUT/TEXTAREA.
  • Entry shape is currently hard-coded to { type: 'reclassify'; changelogId: string } — extending undo to other actions requires either widening this union or just reusing the same type.
  • Stacks are lost on page refresh. Undo state is not persisted.

1.4 IPC surface

src/main/ipc/changelog.ts exposes changelog:list, changelog:revert, changelog:listByRule. The Version History page (src/renderer/pages/VersionHistoryPage.tsx) and RuleDeactivationModal use these for manual revert UI.

1.5 Where undo is actually wired

Only one place: src/renderer/hooks/useReclassification.ts:188 calls pushUndo({ type: 'reclassify', changelogId }) after rules:createAndApply. (Line 37 is where useUndoRedo is initialised; the actual stack push is inside confirmApply.)

4. What It Would Take to Add Undo

4.1 Quick wins low effort

These already log to the changelog — the only change is in the renderer: capture the returned changelogId and call pushUndo().

  • rules:apply — wire up in whatever component triggers bulk rule application. Backend already returns a changelogId.
  • transactions:update — wire up in DataReview / Review pages where cell edits happen.
  • classification:start — slightly trickier because it's fire-and-forget over EventBus; the changelogId would have to be emitted on the completion event.
  • feedback:apply (all 5 subtypes) — capture changelogId in the feedback panel.

Also: widen UndoEntry['type'] from 'reclassify' to a broader union so the UI can label undo toasts meaningfully.

4.2 Medium effort medium — single-table mutations

For each of these, follow the recipe: SELECT old row → write → call changelog.logChange({source:'manual', oldValues, newValues, affectedIds, ...}) → return id → renderer pushes onto undo stack.

  • Supplier: update, confirm, rename, delete, filterTailSpend, parent ops
  • Taxonomy: addNode, updateNode, deleteNode
  • Rules: create, update, delete, setCategoryA, all group ops
  • Project: setSetting, updateMetadata, QC config
  • Transactions: markAllReviewed (capture all affected ids before bulk update)

4.3 Harder high — cascading / multi-table mutations

  • taxonomy:renameNode — cascades into taxonomy children, project_suppliers.mapped_taxonomy_paths, l1_l2_path, and possibly transactions.taxonomy_node_id. The changelog row would need to encode multiple table writes (or be split into multiple linked entries). The current schema only has one affected_table column — this is the main blocker. Options: (a) widen schema to support multi-table changes, or (b) write a parent entry plus N child entries with a shared group_id.
  • taxonomy:mergeNodes / suppliers:merge — same multi-table problem plus deletion of the loser row, which has to be re-created on revert.
  • suppliers:assignAlias — touches many transactions; large old_values payload but otherwise straightforward.
  • suppliers:applyCsvDiff, suppliers:importCSV, taxonomy:importFromFile — bulk inserts of many rows. Realistic approach: store affected_ids only and treat undo as "delete what was inserted, restore what was overwritten".
  • ingest:importCSV / ingest:deleteUpload — intentionally excluded from undo. Users delete uploads manually via the UI; no changelog or undo wiring needed.

4.4 Cross-cutting changes worth doing alongside

  1. Backend should push, not the renderer. Today every caller has to remember to pushUndo(). A nicer pattern: have logChange() emit an EventBus event (e.g. changelog:created) and have useUndoRedo subscribe to it. Then any new logged mutation is automatically undoable, no per-call wiring.
  2. Persist the undo stack per project, e.g. as a row in project_settings or its own tiny table — currently a window reload wipes it.
  3. Multi-table changelog entries. Add a group_id column so cascading operations (rename, merge) can be reverted as a single logical undo step.
  4. Type the undo entries. Replace the hard-coded 'reclassify' with a discriminated union so undo toasts can say "Undid: rename supplier" instead of always "Undid reclassification".
  5. Exclude actions that should never be undoable from the system explicitly (e.g. settings:setApiKey, project create/open/close, exports). A small allowlist/denylist on the backend prevents accidents.
