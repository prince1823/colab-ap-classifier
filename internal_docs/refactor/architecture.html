Colab91 AP Classifier

Post-Refactor Architecture — DI, User-Driven Workflow, Full-Stack Alignment

Overview

Desktop Electron app for automated classification of accounts payable transactions. Users import CSV transaction data, configure taxonomy and company context, run AI-powered classification (with web research on suppliers), then review and correct results.

Key Architectural Decisions

  • Dependency Injection — all services receive dependencies via constructor. No module-level singletons (except EventBus).
  • Interface-first — every service has a clean interface in src/shared/types/services.ts. Consumers depend on abstractions, not implementations.
  • Service Container — a lightweight factory function (createContainer()) wires everything at startup. No DI framework.
  • User-Driven Workflow — research and classification are separate user-triggered actions. No automated pipeline or forced checkpoints. User researches suppliers, reviews results, then triggers classification. Progress is reported via EventBus.
  • EventBus — single typed event emitter replaces 3 setMainWindow() calls. Services emit events; entry point forwards to renderer.

Service Container

The container is a plain factory function — ~60 lines, no framework, no decorators. It instantiates everything in dependency order and returns a typed ServiceContainer object.

File: src/main/container.ts

export interface ServiceContainer {
  // Leaf
  db: Database;
  supplierUniverse: SupplierUniverse;
  eventBus: EventBus;
  llm: LLMClient;
  webSearch: WebSearch;
  // Agents
  classificationAgent: ClassificationAgent;
  researchAgent: ResearchAgent;
  columnMappingAgent: ColumnMappingAgent;
  // Data
  changelog: ChangelogStore;
  transactions: TransactionStore;
  project: ProjectStore;
  taxonomy: TaxonomyStore;
  suppliers: SupplierService;
  rules: RuleStore;
  ingest: IngestService;
  export: ExportService;
  // Orchestrators
  researcher: SupplierResearcher;
  classifier: ClassificationRunner;
}

export function createContainer(): ServiceContainer {
  // Leaf layer
  const db = new DuckDBDatabase();
  const supplierUniverse = new DuckDBSupplierUniverse();
  const llm = new OpenRouterLLMClient();
  const webSearch = new ExaWebSearch();

  // Agents
  const classificationAgent = new LLMClassificationAgent(llm);
  const researchAgent = new LLMResearchAgent(llm);
  const columnMappingAgent = new LLMColumnMappingAgent(llm);

  // Data layer (order matters — respect dependency graph)
  const changelog = new ChangelogStore(db);
  const transactions = new TransactionStore(db, changelog);
  const project = new ProjectStore(db, transactions);
  const taxonomy = new TaxonomyStore(db, project);
  const suppliers = new SupplierService(db, supplierUniverse);
  const rules = new RuleStore(db);
  const ingest = new IngestService(db, transactions, columnMappingAgent);
  const exportSvc = new ExportService(db);

  // Orchestrators
  const researcher = new SupplierResearcher(
    supplierUniverse, webSearch, researchAgent, eventBus);
  const classifier = new ClassificationRunner(
    db, taxonomy, project, rules,
    transactions, changelog, classificationAgent, eventBus);

  return { db, supplierUniverse, eventBus, llm, webSearch,
    classificationAgent, researchAgent, columnMappingAgent,
    changelog, transactions, project, taxonomy, suppliers, rules,
    ingest, export: exportSvc, researcher, classifier };
}

Entry Point: src/main/index.ts

app.whenReady().then(() => {
  const services = createContainer();
  registerAllHandlers(services);  // IPC handlers receive their services
  createWindow();

  // Forward events to renderer
  services.eventBus.on('classification:progress', (...args) => {
    if (mainWindow && !mainWindow.isDestroyed())
      mainWindow.webContents.send('classification:progress', ...args);
  });
  services.eventBus.on('suppliers:research:progress', (...args) => {
    if (mainWindow && !mainWindow.isDestroyed())
      mainWindow.webContents.send('suppliers:research:progress', ...args);
  });
});

Data Flow

End-to-end flow from CSV import to classified export.

1
CSV Import — User selects CSV file. IngestService.parseCSVPreview() reads columns + sample rows. System checks for existing uploads with matching columns to offer stored mappings. If no match: ColumnMappingAgent.suggestMappings() uses LLM to suggest mappings. User reviews/adjusts column mappings. User confirms → mappings saved to uploads table for reuse. IngestService.importCSV() creates transactions with mapped columns. Each row gets upload_id linking back to this upload. Column classification priorities (which columns to send to LLM, in what order) are set separately via project_settings.column_priorities.
2
Project Setup — User configures company context (industry, sector, procurement nuances) via ProjectStore.setSetting('company_context', ...). Imports taxonomy from file (TaxonomyStore.importFromFile()) or creates from text. Optionally creates override rules (RuleStore.createRule()) for known classifications.
3
Research — User clicks "Research All Suppliers" → SupplierResearcher.researchAll(). For each supplier: check SupplierUniverse for existing data → web search fallback → LLM formats → upsert to universe. User reviews research results on Supplier page (normalize names, confirm/reject, assign parents). Normalization sets project_supplier_id FK on each transaction row, linking aliases to their canonical supplier.
4
Classification — User clicks "Classify All" → ClassificationRunner.classifyAll(). For each supplier: retrieves transactions via project_supplier_id FK → apply override rules → LLM classify remaining. Progress reported via events. Runs to completion. No forced checkpoints.
5
Review — User reviews classified transactions. Can accept (sets human_reviewed = true) or reclassify (updates taxonomy_node_id + sets human_reviewed = true). Review status is tracked independently from classification method. All changes logged to change_log table with before/after values. ChangelogStore.revertChange() for undo.
6
Export — ExportService.exportCSV() writes classified transactions with taxonomy paths to CSV.

+ dynamic canonical columns: spend_amount, gl_description, etc. (supplier_name is NOT stored here — derived via JOIN on project_supplier_id)

Key design decisions:

  • upload_id links each row to its source CSV upload, enabling per-upload queries, selective re-import, and future deduplication.
  • human_reviewed is a separate boolean from classification_status. A row can be classified_by_ai + human_reviewed=true (reviewed and accepted), or classified_by_rule + human_reviewed=false (not yet seen by a person). This decouples review tracking from the classification method.
  • classification_status no longer includes "human_reviewed" as a value — that's now a separate field.
  • original_supplier_name preserves the raw CSV value as an audit trail.
  • project_supplier_id is a FK to project_suppliers.id. During normalization, SupplierService resolves raw names to canonical suppliers and sets this FK. All CSV aliases ("AMZN", "Amazon COM", "Amazn US") point to the same project_suppliers row. This means:
    • Retrieval: WHERE project_supplier_id = ? — fast indexed lookup, no string matching.
    • Rename: Update only project_suppliers.supplier_name — zero transaction rows touched.
    • Classification: Get all transactions for a supplier via FK, not by name.
    • Supplier name display: JOIN with project_suppliers to get the canonical name. No denormalized supplier_name column on transactions.

Design notes:

  • parent_supplier_name tracks parent company relationships (e.g., subsidiary → parent). This is NOT a self-reference — it's a business relationship. NULL means standalone supplier or the supplier itself is a parent.
  • data_source tracks provenance: "universe" = found in SupplierUniverse, "web_search" = researched via web + LLM, "manual" = manually entered by user.
  • universe_match is a quick boolean check: was this supplier already known in the universe when we encountered it?

Joined with transactions (for count/spend) and SupplierUniverse (for research data) at query time.

Design notes:

  • Column mappings are confirmed by the user before import and stored per-upload. When re-uploading an updated CSV with the same structure, the stored mappings can be reused without re-running the LLM suggestion step.

Workflow & Progress

User-Driven Phases

Research and classification are separate user-triggered actions. There is no automated pipeline — the user controls when each phase starts.

1
Research Phase — User clicks "Research All Suppliers" → SupplierResearcher.researchAll(). For each supplier: check SupplierUniverse → web search fallback → LLM format → store. Progress emitted via suppliers:research:progress event. User can cancel anytime.
2
Review Research — User reviews supplier research results on the Supplier page. Can normalize names, confirm/reject suppliers, assign parents, re-research individuals. No time pressure — user proceeds to classification when ready.
3
Classification Phase — User clicks "Classify All" → ClassificationRunner.classifyAll(). For each supplier: apply override rules → LLM classify remaining → update transactions. Progress emitted via classification:progress event. User can cancel anytime.
4
Review Classifications — User reviews results on the Review page. Can accept (sets human_reviewed = true) or reclassify individual transactions.

Frontend Wiring Plan (End-to-End Type Safety)

Current target before cleanup: keep Electron IPC as the only boundary and make the renderer DI-friendly.

  1. Contract-first API facade: keep src/renderer/lib/ipc.ts as a thin typed facade that exposes only explicit interface methods.
  2. Per-feature service layer: add src/renderer/services modules (for example projectService, transactionService, supplierService) and keep orchestration there, not in page components.
  3. DI composition root: provide service implementations via context in src/renderer/App.tsx (or a provider file nearby), then consume through custom hooks such as useProjectService.
  4. Shared DTOs + strict mapping: keep shared types as the wire contract; every boundary call is mapped at adapter edges, never partially inferred.
  5. Event bridge: stream listeners in one place (e.g., store adapters) and re-expose normalized UI events to components.

Preferred data flow:

Page/Component → Feature Service → Typed IPC Adapter → preload invoke/event → main IPC handler → DI service/container

Boundary Definition (Renderer ↔ IPC)

Renderer should never call ad-hoc methods. It should call a typed contract map that defines channel, args, and result together.

// Proposed shared contract shape (example)
interface IPCInvokeMap {
  'transactions:query': { args: [filters?: TransactionFilter]; result: PaginatedTransactions };
  'transactions:update': { args: [update: TransactionUpdate]; result: void };
  'suppliers:update': { args: [id: string, input: SupplierUpdateInput]; result: void };
  'export:csv': { args: []; result: { rowsExported: number } | null };
}

type Channel = keyof IPCInvokeMap;
type Args<K extends Channel> = IPCInvokeMap[K]['args'];
type Result<K extends Channel> = IPCInvokeMap[K]['result'];
  • Do not pass string channel names around components.
  • Do not expose any rows from hooks; convert to typed view models once.
  • Keep backend wire DTOs (shared/types) separate from UI view models.
